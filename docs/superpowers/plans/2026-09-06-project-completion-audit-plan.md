# 当前项目完成进度检查计划

> **For agentic workers:** 本计划用于检查项目完成进度，不进行功能开发。执行时不得使用子代理；按清单逐项核验、记录证据，并将最终检查报告保存到 `test/` 目录，按编号递增命名。

**Goal:** 全面确认 InkEdge 当前项目在功能、前端、后端、AI 调用、数据持久化、部署配置、线上可用性和文档沉淀上的完成进度。

**Architecture:** 检查以“用户真实路径”为主线，从静态前端入口出发，核对 API 客户端、Express 本地服务、Worker 线上入口、D1 数据存储和 DeepSeek 模型调用链路。每一项都用明确的通过标准判定为“已完成 / 部分完成 / 未完成 / 需复核”。

**Tech Stack:** Node.js、Express、Cloudflare Worker、Cloudflare D1、Wrangler、静态 HTML/CSS/JS、DeepSeek Chat API、Playwright。

**Spec:** 当前用户要求：再次全方面检查当前项目完成进度，先制定检查计划，写明检查内容、具体评判标准和检查方式。

## Global Constraints

- 不修改业务代码、配置、数据库结构或线上资源，除非用户后续明确要求。
- 不推送 Git，不删除文件夹。
- 如测试启动本地项目进程，测试结束后必须关闭该进程。
- 读取中文文档时不使用 PowerShell 直接读取；优先使用 Node.js UTF-8 读取方式。
- 搜索范围限制在 `D:\tony\黑客松项目` 项目目录内。
- 最终检查报告保存为 Markdown 文档，并包含置信度评估。

## 一、检查输出物

### 1. 完成进度总表

**评判标准：**

- 每个模块必须有当前状态、证据来源、风险点、建议下一步。
- 状态只使用四类：`已完成`、`基本完成`、`部分完成`、`未完成`。
- 不以“代码存在”直接判定完成，必须结合接口、页面或测试证据。

**检查方式：**

- 汇总项目结构、测试脚本、线上接口返回、页面可访问性、历史测试报告。
- 生成最终报告：`test/项目完成进度全方面检查报告-1.md`，如已有同名编号则递增。

### 2. 问题清单

**评判标准：**

- 每个问题必须包含：问题表现、影响范围、可能原因、修复优先级。
- 优先级使用：`P0 阻断`、`P1 重要`、`P2 一般`、`P3 优化`。

**检查方式：**

- 对照功能链路和测试结果记录异常。
- 对线上与本地差异单独标注。

## 二、项目结构与配置检查

### 1. 基础文件完整性

**检查内容：**

- `package.json`
- `server.js`
- `worker.mjs`
- `wrangler.jsonc`
- `public/`
- `lib/`
- `scripts/`
- `migrations/`
- `.env.example`
- `README_AGENT_HANDOFF.md`

**评判标准：**

- 核心入口文件存在。
- 测试脚本与当前功能模块对应。
- Worker 入口与本地 Express 入口职责清楚。
- `.env.example` 不包含真实密钥。

**检查方式：**

- 用 Node.js 枚举文件和读取 JSON 配置。
- 不读取 `.env` 的真实值，只检查是否被 `.gitignore` 排除。

### 2. 部署配置

**检查内容：**

- Worker 名称是否为 `inkedge`。
- 路由是否为 `inkedge.aicreatorhome.cn/*`。
- D1 数据库是否为 `inkedge-state`。
- D1 绑定名是否与代码中读取的绑定一致。
- AI 服务变量是否包含 `AI_API_BASE_URL`、`AI_GUIDANCE_MODEL` 等必要项。

**评判标准：**

- `wrangler.jsonc` 和代码内绑定读取一致。
- 不再残留旧 Worker 名称作为实际部署目标。
- 部署配置中不出现真实 API Key。

**检查方式：**

- 用 Node.js 读取 `wrangler.jsonc` 关键字段。
- 在项目目录内搜索旧 Worker 名、旧 D1 名、敏感密钥模式。

## 三、核心功能完成度检查

### 1. “我还没写，帮我构思”

**检查内容：**

- 作文题目、年级、文体、素材输入。
- 生成构思建议。
- 生成问题并允许用户回答。
- 根据用户回答生成下一步引导。
- 生成提纲树形图。
- 生成段落写作提示。
- 段落输入框。
- “我写完了”合并段落并进入写完流程。

**评判标准：**

- 前端不是只展示空泛建议，必须存在可交互的选择和回答入口。
- 后端接口返回结构化数据，前端能稳定渲染。
- 结果不因请求完成后的状态刷新而闪退或被错误覆盖。
- 至少覆盖一次完整用户路径：输入信息 -> 生成构思 -> 回答问题 -> 生成提纲 -> 段落提示 -> 填写段落 -> 合并作文。

**检查方式：**

- 静态检查 `public/app.js`、`public/api-client.js`、`server.js` 中对应钩子和接口。
- 本地启动服务后用 Playwright 跑一条完整路径。
- 线上域名重复跑一条轻量路径，避免只验证本地。

### 2. “我写完了，帮我体检”

**检查内容：**

- 作文草稿输入。
- 结构、语言、内容问题诊断。
- 返回修改建议。
- 与构思流程合并作文后的跳转关系。

**评判标准：**

- 用户从“我还没写”完成作文后，可以自然进入体检。
- 单独粘贴草稿也能使用。
- 错误提示清楚，不暴露内部异常堆栈。

**检查方式：**

- 检查前端入口和 API 调用。
- 用一篇短作文做本地 API 冒烟。
- 如线上需要消耗模型，使用短文本验证一次。

### 3. “局部修改”

**检查内容：**

- 用户输入局部修改目标。
- 返回修改建议或示范句。
- 不误用长期训练逻辑。

**评判标准：**

- 页面入口存在。
- API 可调用。
- 返回内容与局部修改目标相关。

**检查方式：**

- 静态检查前端入口和 API 方法。
- 用一段短文本做接口冒烟。

### 4. “个性化训练 / 7 天训练计划”

**检查内容：**

- 只保留 7 天计划入口。
- 去掉 14 天、30 天、考试冲刺等无关预填项。
- 创建 7 天训练计划。
- 七个阶段顺序：
  - `topic_angle`
  - `material_questions`
  - `outline_tree`
  - `paragraph_guides`
  - `paragraph_drafting`
  - `draft_diagnosis`
  - `revision_reflection`
- 每天任务能根据上一阶段产物推进。
- 第 1 天不只是建议，而是输出可选择角度。
- 第 2 天输出素材追问。
- 第 3 天输出提纲树。
- 第 4 天输出段落提示。
- 第 5 天支持段落草稿输入或整合。
- 第 6 天诊断完整草稿。
- 第 7 天生成复盘与下一步建议。

**评判标准：**

- 本地测试 `test:training-plan-7d` 通过。
- 前端测试 `test:short-guidance-frontend` 通过。
- 线上创建计划和执行第 1 天成功。
- 若要判定“接近我还没写板块完成度”，需要至少手动或自动跑通第 1 天到第 4 天；第 5 天到第 7 天至少接口可用并返回结构化内容。

**检查方式：**

- 执行现有测试脚本。
- 用线上临时用户创建计划并调用任务运行接口。
- 如写入远程 D1，检查完成后删除临时测试记录并二次确认。

### 5. 学习档案 / 成长 / 错因本

**检查内容：**

- 用户档案接口。
- 能力画像接口。
- 成长时间线接口。
- 错因记录或训练反馈入口。

**评判标准：**

- 页面入口存在或明确标记为暂未完善。
- API 不返回 500。
- 若当前只是占位，必须在完成度报告中标为“部分完成”或“未完成”，不能算已完成。

**检查方式：**

- 检查对应前端页面和服务端接口。
- 用轻量请求验证返回格式。

## 四、AI 调用链路检查

### 1. DeepSeek 接入

**检查内容：**

- API Base URL 来源。
- API Key 是否只来自环境变量或 Cloudflare Secret。
- 指导模型、检测模型、改写模型配置。
- 请求超时、失败重试、错误提示。

**评判标准：**

- 代码中不硬编码真实 Key。
- 前端不能直接接触 Key。
- 模型失败时用户看到可理解提示。
- 本地无 Key 时有合理降级或明确报错。

**检查方式：**

- 敏感信息扫描。
- 本地无 Key 测试。
- 线上短输入模型调用测试。

### 2. 提示词与结构化输出

**检查内容：**

- 短期构思指导提示词。
- 7 天训练各阶段提示词。
- 输出 JSON/结构化字段约束。
- 模型输出解析失败时的兜底。

**评判标准：**

- 不依赖模型自由发挥来决定前端结构。
- 每个前端组件需要的字段都有默认值或兜底。
- 失败时不会导致页面空白。

**检查方式：**

- 检查 `lib/essay-guidance.js`、`lib/seven-day-training-runner.js`、`server.js`。
- 用正常输入和异常输入各测一次。

## 五、前端 UI 与交互检查

### 1. 页面入口与导航

**检查内容：**

- 首页入口。
- App 主页面。
- 训练计划页面。
- 账号页面。
- 返回、跳转、导航状态。

**评判标准：**

- 用户能从首页进入主要功能。
- 不出现旧 UI 残留导致的误导入口。
- 移动端和桌面端都能阅读。

**检查方式：**

- 用 Playwright 分别检查桌面和移动视口。
- 保存必要截图到测试记录中描述，不必大量截图入库。

### 2. 表单与状态管理

**检查内容：**

- 按钮 loading 状态。
- 请求完成后结果是否保留。
- 错误提示是否准确。
- 用户多次点击是否会造成重复请求或状态错乱。

**评判标准：**

- 结果生成后不会闪一下消失。
- 失败提示不覆盖已有可用结果，除非确实是新请求失败。

**检查方式：**

- 本地和线上各触发一次主要按钮。

### 3. 视觉完成度

**检查内容：**

- 文本是否溢出。
- 卡片、按钮、输入框是否对齐。
- 深浅主题是否可用。
- 7 天计划阶段产物是否有清楚层级。

**评判标准：**

- 主要功能区域无明显遮挡、重叠、错位。
- 长文本能换行。
- 移动端不需要横向滚动才能完成主要流程。

**检查方式：**

- Playwright 截图检查。
- 针对生成结果较长的场景手动滚动检查。

**检查内容：**

- 当前部署版本 ID。

**检查方式：**

## 十一、进度判定口径

### 已完成

- 功能入口存在。
- 前端能完成用户路径。
- 后端接口可用。
- 数据可保存或读取。
- 自动测试或冒烟测试有证据。
- 线上可用。

### 基本完成

- 主路径可用。
- 存在小 UI 问题、边界输入问题或个别体验不足。
- 不影响用户完成核心任务。

### 部分完成

- 有入口或部分接口。
- 只能完成局部路径。
- 缺少关键交互、结构化输出或线上验证。

### 未完成

- 无入口、无接口，或接口不可用。
- 用户无法完成对应任务。
