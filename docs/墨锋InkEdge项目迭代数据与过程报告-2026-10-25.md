本报告不会虚构以下数据：

- 注册用户总数。
- 日活、月活和留存率。
- AI 调用总次数和总 Token。
- 作文平均提分。
- 邮件实际到达率。
- 收入、付费率或转化率。

这些属于生产运营数据，需要独立埋点和统计系统支持。

## 三、迭代阶段时间线

### 阶段一：作文引导主链建立（2026-08-23 至 2026-08-24）

主要目标是把“给一个题目直接生成作文”改造成可交互写作引导。

完成内容：

- 创建作文会话。
- 输入题目、年级、文体和真实素材。
- 题目理解和立意方向。
- 素材追问。
- 提纲树和分段提示。
- 段落输入、合并草稿和进入修改。
- 短篇写作引导和异常处理方案。
- Render 部署说明和本地运行基础。

这一阶段的核心决策是：**AI 不直接代写最终作文，而是先帮助学生做选择和回忆。** 这个决策决定了后续素材、训练、体检和成长模块的数据结构。

### 阶段二：7 天训练与 Cloudflare 基础（2026-08-24 至 2026-08-25）

主要目标是让一次性作文引导变成可持续的阶段训练，并建立生产部署能力。

完成内容：

- 7 天单篇作文训练计划。
- 阶段顺序、阶段输入和阶段产物保存。
- Worker 名称统一为 `inkedge`。
- D1 数据库统一为 `inkedge-state`。
- 自定义域名和线上健康检查。
- 部署脚本和 dry-run 模式。
- 深浅主题和 Apple 风格初版。

线上历史报告曾验证计划创建、Day 1 模型调用、活动计划读取和 D1 测试数据清理。

### 阶段三：完成度审计、成长和训练状态机（2026-09-06）

这一阶段不是简单增加页面，而是进行全项目完成度检查，暴露接口、前端状态和历史功能残留问题。

主要发现包括：

- Dashboard 聚合函数曾缺失并导致 500。
- 浏览器写作引导链路存在长等待或状态反馈问题。
- 训练计划 Day 5 较依赖本地合并。
- 游客 IP 管理和折叠指示器曾出现失败。
- 历史 14 天、30 天计划文案与当前 7 天定位不一致。

随后完成：

- 重建训练计划前端 7 阶段状态机。
- 完善阶段停留、查看结果和手动进入下一阶段。
- 成长时间线从业务记录聚合生成。
- 修复构思读取真实素材。
- 移除不再需要的错因本独立入口并调整总览。

这一阶段建立了重要方法：**通过完成度报告识别“页面存在”和“真实流程可用”之间的差距。**

### 阶段四：真实素材、全功能修复与 UI 提升（2026-09-13）

主要目标是补齐素材、能力、训练质量和界面一致性。

完成内容：

- 素材库改为只输入真实素材，由模型自动分类和生成适用题目。
- 构思、素材、提纲、段落提示、体检和修改进行真实作文抽样。
- 写作引导拆分模型调用，降低长 JSON 解析失败。
- 八维能力画像和成长相关展示增强。
- 7 天训练多个阶段进行真实 AI 链路检查。
- UI/UX 进行大范围规划和局部修复。
- 形成学生与家长介绍文档。

这一阶段的关键变化是：**把素材真实性从输入要求提升为产品原则。** 模型可以帮助分类和组织，但不应把生成细节冒充用户经历。

### 阶段五：立意优先与浏览器批注驱动迭代（2026-09-27）

主要目标是优化“我还没写”的顺序和页面操作体验。

完成内容：

- 先生成和选择立意，再生成素材追问。
- 选择非第一项立意也能继续流程。
- 支持补充素材追问和继续回答。
- 形成浏览器批注 UI 调整计划。

这一阶段的产品决策是：**素材追问必须围绕用户选择的立意，而不是模型默认方向。** 这减少了问题泛化，也提高了学生的控制感。

### 阶段六：参考对照和作文修改流程收口（2026-10-06 至 2026-10-07）

主要目标是解决参考稿只改标点、按钮位置不合理、上下文缺失和移动页面体验问题。

过程包括：

1. 建立参考对照页面和 API 合同。
2. 用真实作文测试，发现参考稿只做标点和衔接调整。
3. 增加实质修改检查和改动说明。
4. 根据用户批注调整流程：局部修改按钮必须在体检完成后出现。
5. 移除体检卡片中过早出现的参考对照入口。
6. 把体检优先问题与局部修改建议一起传给参考稿模型。
7. 去掉参考稿提示中的过度事实限制，允许更充分重组人物、事件、细节和结构。
8. 在参考对照页顶部显示优先问题，并修复返回链接。
9. 增加浅色主题。

这一阶段体现了一个重要质量原则：**接口返回成功不等于产品质量通过。** 真实作文结果必须落实诊断问题，不能只满足 JSON 格式。

### 阶段七：账号、SMTP、D1 归属和计费边界（2026-10-07）

主要目标是复现成熟的登录体验，并将所有用户数据真正绑定账号。

完成内容：

- 复用参考项目的邮箱验证码登录/注册界面和交互。
- 复用现有 `inkedge-state`，没有新建重复 D1。
- SMTP 配置进入 `.env` 和 Cloudflare Secret 管理。
- 本地模拟 SMTP 完成发送、校验、Cookie 和用户持久化链路。
- 登录后账号入口跳转个人中心。
- 作文、素材、能力、训练、成长和改写任务统一按真实账号 ID 归属。
- 游客数据在登录后迁移到账号。
- 删除算力余额、费率、流水、游客额度和管理员调额度 UI。
- 检测、改写和训练停止余额检查与扣减。
- 保留微信收款码图片。
- 历史计费接口返回 `410`。

这是本项目后期最重要的架构变更之一：**账号从一个界面功能升级为所有学习数据的归属边界。**

### 阶段八：结项核对与交付（2026-10-25）

本阶段没有扩大产品范围，主要完成：

- 按最新报告优先原则重新核对项目事实。
- 枚举当前页面、业务模块、API、测试和文档数据。
- 执行 21 项当前语法与回归检查。
- 对生产站健康、页面文案、主题和历史计费接口做只读核对。
- 生成结项完成进度报告。
- 生成面向用户的使用说明。
- 生成本迭代数据与过程报告。

## 五、缺陷发现与修复数据

过程报告中可以确认的典型缺陷类别：

| 类别 | 代表问题 | 最终处理 |
| --- | --- | --- |
| 流程顺序 | 局部建议按钮在体检前可见 | 改为体检成功后动态出现 |
| 入口归属 | 参考对照入口出现在体检卡片 | 移到局部修改建议区域 |
| 上下文缺失 | 参考模型未收到体检优先问题 | 服务端从已保存诊断读取并传入 |
| 模型质量 | 参考稿只改标点或少量词语 | 调整提示词和实质修改要求 |
| 页面链接 | 返回按钮指向 `/app` 空地址 | 统一为 `/app.html` |
| 主题 | 参考对照只有深色 | 加载共享主题脚本并补浅色样式 |
| 账号入口 | 已登录点击账号仍打开登录弹窗 | 已登录时跳转个人中心 |
| 数据归属 | 客户端可携带任意用户 ID | 改为服务端认证账号 ID |
| 商业逻辑 | 算力文案和余额仍出现在移植页面 | 移除 UI、扣减和管理接口 |
| 状态渲染 | 强力模式事实审计为 `null` 时可能中断 | 增加空值兼容回归 |
| 数据显示 | `escapeHtml(0)` 被显示为空 | 改为空值合并并加测试 |
| 训练体验 | 阶段结果生成后可能立即跳走 | 状态机停留展示，由用户继续 |

这组问题说明后期迭代主要集中于四个方向：流程顺序、数据归属、模型上下文和前端状态一致性。

## 七、部署与数据演进

### 7.1 部署形态

项目从普通 Node 本地运行扩展到 Cloudflare Worker：

- `worker.mjs` 使用 Node HTTP 兼容方式承载 Express。
- 静态文件由 Worker Assets 提供。
- 自定义域名路由到 `inkedge` Worker。
- `/health` 用于部署后确认。

### 7.2 D1 选择

项目最终复用 `inkedge-state`，没有复制参考项目的 `ai-text-detector-state`。这避免了两个项目之间用户和业务数据混用。

D1 采用通用记录表：

- `app_state_records` 保存业务集合 JSON。
- `security_rate_limits` 保存安全限流数据。

该结构使本地 JSON 状态和云端 D1 状态可以共享大部分业务代码，但长远看仍可考虑把核心实体迁移为更明确的关系表。

### 7.3 账号归属

早期接口较多依赖前端传入用户标识。最终版本改为：

- 登录用户读取服务端会话中的账号 ID。
- 游客使用服务端签发的 Cookie 标识。
- 登录成功后迁移游客数据。
- 作文会话执行所有权检查。

这使数据存储从“功能可演示”升级为“可以支持真实多用户”。

### 7.4 商业数据边界

早期状态和接口包含算力、流水、充值和游客额度。2026-10-07 明确改为不使用算力计费：

- 前端不显示。
- 后端不校验、不扣减。
- 管理接口下线。
- 历史字段保留兼容，不物理清空 D1。

这个处理避免了破坏历史数据，也让未来收费方案可以独立设计。

## 八、过程中的有效做法

### 8.1 最新报告优先

同一功能在不同阶段会发生变化。例如早期报告仍描述算力系统，最新报告已经将其移除。结项时必须以最新证据覆盖历史描述，否则会把已下线功能写成现状。

### 8.2 计划不能当作完成证据

本项目有 16 份方案文档。方案只能说明计划做什么，必须结合源码、测试或部署记录才能标记为完成。

### 8.3 真实模型测试不能被假模型合同替代

参考对照曾经所有合同测试通过，但真实输出只修改标点。假模型适合验证结构和上下文，不能证明实际写作质量。

### 8.4 页面批注直接驱动流程改进

按钮位置、返回链接、问题卡片和主题等多项改动来自真实页面批注。对用户体验问题，带目标元素的批注比抽象需求更容易形成可验证修复。

### 8.5 数据归属必须由服务端决定

客户端传入 `userId` 方便早期演示，但不适合真实账号。最终改为服务端会话归属，是项目从原型到可用产品的重要分界。

### 8.6 历史接口应明确下线

旧计费接口返回 `410`，比继续返回空数据或悄悄忽略更清楚。调用方可以知道协议已经停止，而不是误判为暂时没有余额。

## 九、过程中的不足

### 9.1 单文件后端仍然较大

`server.js` 已达到 4,646 行。虽然业务逻辑已经部分拆入 `lib/`，认证、状态、API 和模型编排仍集中。下一阶段若继续扩大功能，建议按认证、作文、训练、改写和云状态拆分路由或服务。

### 9.2 测试门禁不统一

项目有较多测试脚本，但没有一个统一命令自动完成所有非真实 AI 检查，并根据环境决定是否运行浏览器和真实 AI。测试脚本也出现新安全契约与旧测试不一致的问题。

### 9.3 过程指标缺少自动采集

当前可以统计文件和报告，但不能回答真实用户使用效果。后续若进入运营，需要建立匿名、合规且可关闭的产品指标，例如：

- 构思流程完成率。
- 体检到局部修改转化率。
- 7 天计划阶段完成率。
- 参考稿生成成功率和重试率。
- 邮件验证码发送成功率。

### 9.4 模型质量仍需固定样本集

项目已经做过多篇真实作文测试，但缺少固定回归样本和评分标准。建议建立一组不含隐私的代表性作文，长期观察诊断、修改幅度、事实偏移和语言自然度。

### 9.5 历史文档存在过期信息

部分较早交接说明仍描述算力、余额和游客额度。它们作为历史记录有价值，但新接手者必须优先阅读最新结项报告和当前源码。

## 十、后续迭代建议

如果启动下一期，建议按以下顺序：

1. 更新 5 个旧测试脚本，建立统一的非真实 AI 全量测试命令。
2. 建立固定作文质量样本集和参考稿人工评分表。
3. 增强 Day 5 逐段反馈、输入自动保存和恢复。
4. 增加生产错误监控、邮件投递监控和 D1 备份流程。
5. 拆分 `server.js`，降低认证、训练和改写模块之间的修改影响。
6. 在商业模式明确后单独设计收费，不恢复旧算力字段作为临时方案。

## 十一、过程总结

墨锋 InkEdge 的迭代不是简单堆叠功能，而是经历了三次明显升级：

1. 从“AI 生成内容”升级为“学生参与选择、回忆、写作和复盘”的教学流程。
2. 从“单次页面演示”升级为“7 天计划、素材、能力和成长记录”的连续训练系统。
3. 从“匿名原型”升级为“邮箱账号、服务端归属、D1 持久化和生产部署”的多用户产品。

后期改动进一步明确了产品边界：不启用未规划好的算力收费；参考稿必须同时使用体检问题和局部建议；账号必须成为数据归属来源；真实模型质量必须单独验证。

这些过程数据和决策可以作为下一期开发的基线。未来新增功能应尽量沿用当前“真实素材、明确阶段、可解释反馈、服务端归属、最新证据优先”的原则。

## 十二、置信度评估

综合置信度：**0.95**。

高置信度部分包括文件数量、路由数量、测试资产、报告数量、当前源码结构和生产站只读状态。阶段时间线主要来自对应日期的方案和测试报告。低于完全确定的部分是早期未记录的开发活动和无法从仓库推导的实际运营数据；这些内容已明确排除，没有用估算代替事实。
